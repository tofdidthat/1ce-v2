# 1CE v2 — PR #27 (S2) security release and rollback checklist

**Status:** Draft PR, branch-only. This file authorizes no database migration, merge, production deploy, R2 write, cleanup or account testing. A second AI should review the exact PR diff, final-head CI and remaining risks before the user approves a release.

## Current S2 decision and implementation (authoritative update)

**DECISION:** Store future account quotas by **plan**, not as one Railway-wide `V2_MAX_STORED_GIB` value. The PR creates only the `default` entitlement (10 GiB as a conservative *technical starting value*, not a paid tier or subscription); future plan names, prices and capacities are not yet decided. An unassigned account inherits `default`. `v2_storage_plans` holds per-plan byte limits, and `v2_account_storage_plans` holds optional server-controlled assignments; both are additive in SQL **011**. The client cannot self-assign a plan. Upgrades don't duplicate assets; downgrades don't delete existing READY data, but prevent new reservations exceeding the new limit.

**Security complement completed in PR code:** Per-file PostgreSQL completion leases with **10-minute expiry and token-fenced READY update** prevent redundant concurrent R2 copies across replicas without retaining a DB connection during streaming. Contenders receive 409 and can retry. Recovery after a crashed worker may require waiting until the lease expires. Login now limits **failed** password guesses only; a valid password remains usable despite hostile failures. Rotating unknown identities share one bounded limiter subject; malformed payloads do not allocate rate rows. Local scrypt concurrency is limited to eight. Remaining edge/WAF and abuse/availability policy requires infrastructure-level review.

**Rate-table housekeeping:** `pruneExpiredRateLimits` deletes rate rows older than **7 days** in batches of 500 using indexed `FOR UPDATE SKIP LOCKED`. An **opt-in** runner `apps/api/scripts/s2-rate-limit-cleanup.mjs` processes at most 10,000 rows per invocation when `V2_RATE_LIMIT_CLEANUP_ENABLED=true` and the isolated v2 `DATABASE_URL` are explicitly supplied. The **schedule is NOT created or active**; propose a once-daily v2-only cron after deployment approval and confirm monitoring. Do not reuse v1 credentials.

**Additive migration order:** **010 first, then 011, then API deployment**, and only with user authorization. GitHub Actions creates a disposable local PostgreSQL, applies both migrations twice, checks the account-plan default and per-user isolation, concurrent lease acquisition/fencing, rate cleanup and shared throttling. No production database was changed.

**Remaining scope separation:** PR #27 does not create plans/billing UI, manipulate subscription payments, delete READY R2 objects or implement Settings → Trash. Those belong to later explicit releases (Trash in PR #28). The 24-hour `staging/` lifecycle is separate from the proposed 30-day Trash recovery window.

## Architecture and invariant

- API: `apps/api/src/library-files.js`, `upload-security.js`, `api-rate-limits.js`. Existing frontend `PUT uploadUrl` contract is unchanged.
- Every signed PUT URL is for `staging/users/<id>/assets/<kind>/<uuid>.<ext>`, with 300-second expiry, declared MIME and length. It is NEVER the `object_key` of a READY file.
- `complete` checks ownership, pending age (30 minutes), metadata and a **nonempty source ETag (fail-closed)**, then performs an **ETag-conditional** copy of staging with server-side R2 credentials to a fresh `.../verified/<uuid>.<ext>` key. It reads **the final copy** to verify exact SHA-256, exact byte count and media signature/ZIP structure before atomically updating `object_key` and `status='ready'`. A still-live signed PUT can only affect disposable staging. No existing READY keys are migrated.
- Verification reads are streaming (SHA-256, bounded 4096-byte prefix/16-byte tail), with byte cap equal to declared size, per-kind timeout (audio 120 s, cover 45 s, stems 180 s). ZIP reads EOCD/central directory and matching local header names with bounded ranges; max 200 entries, 2 MiB central directory, 2 GiB total uncompressed, 1 GiB per entry, 1000x ratio, no encryption, symlink, path traversal, unsupported compression, ZIP64 or multi-disk. This is a defensive structural inspection, **not** a full audio/image decoder or archive decompression scan.
- Account quotas: at most 10 recent pending files (30-minute window), READY + recent pending bytes limited by the user's server-side database plan; unassigned accounts use the 10 GiB default plan seeded in SQL 011. No payment system or other tier values are implemented. Upload initiation remains serialized per owner with a PostgreSQL advisory transaction; 240 init/hour and 360 completes/hour retain shared rate limits.
- Login: 20 **failed** attempts/15 minutes per known account (hashed normalized email); a correct password still works after adversarial failures. Unknown emails share one hashed bucket to bound row growth. Per-process scrypt concurrency is capped at eight. Never trust an unverified forwarded IP; edge/WAF controls remain a separate policy decision.
- Migration: `history/database/010_api_rate_limits.sql` creates the shared throttle table; `history/database/011_storage_plans_completion_leases.sql` creates the per-plan entitlements and upload leases. **Apply 010 THEN 011 before deploying the new API**, or login/upload endpoints fail closed. Never apply to v1.

## Pre-release checks already runnable without production access

- **Automated PostgreSQL migration gate:** GitHub Actions job `s2-postgres-migration-smoke` starts a disposable PostgreSQL 16 database named `onece_s2_ci`, applies SQL 010 twice and verifies index/table, hashed subjects, 30 concurrent UPSERT requests and window expiration. The script `apps/api/scripts/s2-migration-smoke.mjs` refuses any database other than local `onece_s2_ci`. This is evidence of migration syntax/concurrency, **not** evidence that production was migrated.
- **R2 compatibility documentation:** Cloudflare officially lists `CopyObject` source `x-amz-copy-source-if-match` and ranged `GetObject` as supported, and provides prefix-scoped object lifecycle rules. Source: https://developers.cloudflare.com/r2/api/s3/api/ and https://developers.cloudflare.com/r2/buckets/object-lifecycles/ . Cloudflare's advertised compatibility does not replace a real credentialed test.
- **Opt-in real R2 smoke:** `apps/api/scripts/s2-r2-smoke.mjs` requires a dedicated, separate bucket named `onece-s2-smoke-<suffix>` and `R2_SMOKE_ACCOUNT_ID`, `R2_SMOKE_KEY_ID`, `R2_SMOKE_SECRET`, `R2_SMOKE_BUCKET` set privately in the executor. It refuses a name outside this pattern and refuses the app's `R2_BUCKET_NAME` if supplied. It creates only random keys under `s2-smoke/<uuid>/`, tests signed PUT, HEAD, source-conditional copy, ranged GET, overwrite isolation, stale ETag rejection, then attempts to delete only its own keys. **Not automatically run by GitHub Actions; do not paste R2 credentials in chat, commit them, or reuse the production media bucket.** A human with approved, restricted test-bucket credentials must trigger it in a secure execution environment.
- **Lifecycle configuration proposal — DO NOT apply silently:** In Cloudflare R2, select the actual app bucket → Settings → Object Lifecycle Rules → Add rule. Rule name `1ce-v2-staging-expire-24h`; action expire/delete objects after **1 day**; filter/prefix **exactly `staging/`** (not blank, `users/`, `assets/` or `s2-smoke/`). Review every field and preserve existing lifecycle rules. This is a draft operator checklist; no bucket setting has been changed. Cloudflare notes deletion may lag expiration, so do not use a lifecycle rule as a real-time quota counter.
- **Capacity policy:** The user selected plan-based storage. SQL 011 seeds only a conservative 10 GiB `default` plan until the product defines future plan names and capacities; no paid tiers or entitlement management UI are implemented. Project deletion deliberately returns `mediaRetained:true`, retaining `library_files` and R2 objects for shared references and future Trash. Storage used by READY assets does **not** become available when projects are deleted. Do not promise quota reclamation until PR #28 includes safe reference-counting/garbage collection. This limitation requires explicit product acceptance before broad onboarding; avoid enforcing an arbitrary global 10 GiB setting as a substitute for plan data.
- **R2 completion leases:** The DB-backed per-file token prevents concurrent `complete` calls from copying/reading R2 redundantly; 409 means finalization in progress. Lease timeout is 10 minutes; confirm production durations and recovery behavior in monitoring.

- **Residual risk:** ID3 metadata-only spoofing is blocked by bounded checks of two consecutive MPEG Layer III frame headers, but neither this nor the ZIP central/local-header parser is a full media decoder, decompression analysis or antivirus scanner. Run tests with representative real creator files before release.

## Rollback and incident response

- If API fails on deploy, restore the last known-good Railway deployment from S1 and confirm `/health`, `/health/db`, auth and existing media. The additive throttle table can safely remain unused; do not drop it during emergency rollback.
- Never revert `library_files.object_key` to a staging key for any new READY row; it references the server-verified final object. Old S1 code can still read these keys because it uses the DB key transparently, but **old upload completion logic** must not be used for newly staged uploads during rollback.
- Preserve existing ready objects, pending records and R2 data. Never bulk-delete `staging/` or `users/<id>/assets/<kind>/verified/` during rollback. Use a separately reviewed R2 lifecycle policy to expire unreferenced staging keys only after signed URLs and retry windows have elapsed; this PR does **not** install that policy.
- Before release, review and configure an R2 object lifecycle rule scoped strictly to the `staging/` prefix (for example, expiration after 24 hours). Confirm it cannot match `users/` READY objects. This is a separate production configuration action requiring explicit approval; no rule was created in this PR.
- If the new CopyObject API is incompatible with R2 or legitimate uploads fail signature checks, roll back the API and investigate with synthetic test assets. Do not bypass verification in production or silently mark unverified media READY.
- Operational maintenance for throttle rows (not executed here): `DELETE FROM v2_api_rate_limits WHERE window_started_at < now()-interval '7 days';` Schedule only after review; table otherwise grows with unique subjects.
- Existing S1 READY keys were signed before PR #27; they are **not** retroactively copied into verified storage. Previous signed URLs expire after their original TTL. No v1 assets are touched.

## Security review residual concerns (not solved by mocked tests)

- **Completion lease residuals:** cross-instance per-file lease is implemented with token fencing and real PostgreSQL arbitration tests. Expiration (10 min), orphaned copies from interrupted processes and R2 execution times must still be observed in real integration tests; do not claim worker-queue or crash-recovery guarantees.
- **Login overload and maintenance:** valid passwords bypass the failed-attempt limit, unknown emails share one bucket and local scrypt concurrency is capped. A flood against known addresses still costs hashing work; edge/WAF defenses remain future integration. A bounded seven-day row-pruning command exists but **has no production schedule yet**.
- **Storage plans and recovery:** the DB now reads per-user plan entitlements with a seeded default; no commerce/plan tier pricing was invented. Deleting a project still retains shared media, and Settings → Trash plus physical reclamation remain **PR #28**. No code in PR #27 purges READY assets from R2.
- **Media compatibility:** HEAD/CopyObject fail-closed unit tests and structural fixtures (MP3/WAV/PNG/JPEG/WebP/ZIP) ran in CI; test representative real production-format files in a disposable R2 bucket before release. No antivirus or full codec decoding is claimed.
